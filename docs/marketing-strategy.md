# Marketing and Adoption Strategy

This is an internal planning document, not a description of shipped marketing. It is grounded in what the repository actually contains and flags claims that the product cannot support yet.

> **Positioning in one sentence:** CMS is an AI-assisted headless CMS and app builder for developers who want to describe a data model and get entities, seed data, queries, and pages — while keeping a conventional REST/GraphQL backend they can inspect and extend.

---

## 1. What is true today

Use these as the factual basis for any public copy.

| Capability | Evidence in the repository | Marketable? |
|---|---|---|
| AI chat designs entities, relationships, seed data, queries, and pages | `packages/service/src/agent/`, Studio at `/app/` | ✅ Yes |
| Four web surfaces: Studio, Admin, Portal, Stash | `packages/app`, `admin`, `portal`, `stash` | ✅ Yes |
| Offline-first PWA with bookmarks, TTS, and media conversion | `packages/stash`, `packages/service/public/static` | ✅ Yes |
| REST and GraphQL APIs generated by the CMS | CMS-owned `/api` and `/graphql`, proxied by the service | ✅ Yes |
| Single Docker image with Node, .NET, Nginx, ffmpeg | `mono-deploy-local/Dockerfile` | ✅ Yes |
| SQLite, PostgreSQL, MySQL, SQL Server support | CMS configuration (`DATABASE_PROVIDER`) | ✅ Yes, owned by CMS |
| Self-hosted and open source | Repository license | ✅ Yes |
| No local .NET installation needed when using the image | Image bundles the ASP.NET Core runtime | ✅ Yes, word carefully |
| No-code / fully automatic app building | Not implemented | ❌ No |
| Published SDK on npm | `@cms/sdk` is a private source workspace | ❌ No |
| Benchmarks or time-savings percentages | No measurements exist | ❌ No |
| Managed cloud, marketplace, template gallery | Not implemented | ❌ No |

### Claims to avoid

- **"No .NET required."** The Docker image bundles an ASP.NET Core CMS runtime. What is true is that users do not need to install the .NET SDK locally.
- **"Build a full app in 5 minutes."** The AI pipeline is real, but end-to-end results depend on the prompt, model, and CMS state. Do not publish timings that have not been measured.
- **"10× faster", "80% less code".** No benchmark exists. Replace with a concrete demo and let viewers judge.
- **"No-code."** The product still expects users to understand entities, APIs, and React for anything beyond generated pages.
- **"Works with any database out of the box."** The CMS supports several providers, but the image and Compose files are tested around SQLite and PostgreSQL.
- **Demo URLs and template repositories that do not exist.** Do not list `blog.cms.dev`, `shop.cms.dev`, or `examples/*` until they are built.

## 2. Audiences

### Primary: full-stack and frontend developers

They want to skip schema boilerplate and CRUD plumbing, but keep code ownership. They care about:

- a real REST/GraphQL API,
- React integration,
- self-hosting,
- exportability and escape hatches.

Message: *"Describe the data model. Get a real API, seed data, and an admin UI — then keep building in React."*

### Secondary: self-hosters and homelab users

They want one container, SQLite by default, no vendor account.

Message: *"One image, SQLite or Postgres, your data on your hardware."*

### Tertiary: agencies and small product teams

They want fast prototypes that can become maintainable projects.

Message: *"Prototype the backend in an afternoon, then hand the API contract to your frontend team."*

### Not a target (yet)

- Non-technical users looking for a website builder.
- Teams needing SSO, compliance certifications, or a managed SLA.
- High-scale production workloads without an external database and operational review.

## 3. Content plan

### 3.1 Demo videos

Each video should show a real, reproducible flow and state its prerequisites.

| Idea | What to show | Notes |
|---|---|---|
| **Entity to API** | Prompt an entity, inspect the schema, call `/api/entities/<name>` | Strongest proof point |
| **Seed data and query** | Generate records, build a query, open the REST endpoint | Shows the pipeline end to end |
| **Page generation** | Prompt a page, preview it, edit a component | Visual payoff |
| **External React app** | Vite proxy, login, list records, asset URLs | Follows the existing guide |
| **Offline Stash** | Save a bookmark, go offline, play cached media, use TTS | Differentiated feature |
| **Docker in one command** | Run the image, create the admin, build a schema | Removes setup friction |

Production rules:

- show the actual UI and actual errors;
- include the CMS version or image tag;
- link to the exact guide used;
- do not claim a build time unless it is measured in the video.

### 3.2 Written content

Technical posts that match shipped functionality:

- "How the CMS agent pipeline turns a prompt into a schema"
- "What the Fastify BFF does (and what the .NET CMS owns)"
- "Building an external React frontend against CMS"
- "Offline-first content with Stash and IndexedDB"
- "Running CMS with SQLite vs PostgreSQL"

Avoid comparison posts that assert performance or feature superiority without measurements. A factual comparison of architecture is fine; a benchmark table is not.

### 3.3 Documentation as marketing

The most credible asset is the documentation set:

- [Setup](./wiki/Setup.md) for a working local environment,
- [Architecture](./wiki/Architecture.md) for the runtime boundary,
- [API Reference](./wiki/API-Reference.md) for integration,
- [Docker Deployment](./wiki/Docker-Deployment.md) for operations,
- [Known limitations](../README.md#️-known-limitations) for honesty.

Link these from every post and video description.

## 5. Launch checklist

### Before any public launch

- [ ] Verify the Docker quick start on a clean machine.
- [ ] Verify the SQLite path and volume persistence across restarts.
- [ ] Confirm the `.NET CMS` boundary is explained in the README.
- [ ] Remove or qualify every unmeasured performance claim.
- [ ] Publish at least one reproducible end-to-end demo.
- [ ] Document the security model, including plaintext AI keys and missing role checks.
- [ ] Decide the license and contribution process.

### Launch assets

- [ ] One 60–90 second demo with captions.
- [ ] One written walkthrough with commands and screenshots.
- [ ] A pinned issue for known limitations.
- [ ] A support channel that will actually be monitored.

### Channels

Choose channels where developers already discuss headless CMS and self-hosting:

- dev.to / Hashnode / Medium for technical posts;
- Hacker News "Show HN" only with a working demo and honest limitations;
- Reddit communities that allow project posts (read each community's rules);
- Docker Hub and GitHub as the primary distribution surfaces.

Do not mass-post the same copy across communities. Tailor the first paragraph to each audience.

## 6. Adoption metrics

Track metrics that reflect real use, not vanity:

| Metric | Why it matters |
|---|---|
| Successful `docker run` → setup wizard completion | Measures onboarding friction |
| Schemas created per active instance | Measures whether the AI pipeline is used |
| Queries or pages generated | Measures depth of use |
| External frontends built against `/api` | Measures platform value |
| Returning instances after 7/30 days | Measures retention |
| GitHub issues with reproductions | Measures engagement quality |

Stars, Docker pulls, and Discord members are useful distribution signals but say little about whether the product works. Keep them as secondary metrics.

Set targets only after a baseline exists. Do not publish aspirational numbers as current results.

## 8. Summary

The honest story is stronger than the inflated one:

- a working AI-assisted schema and page pipeline,
- a conventional API and admin surface underneath it,
- a single self-hostable image,
- an offline companion app,
- and clear documentation of the boundary and limitations.

Lead with a reproducible demo. State what is not built. Let developers evaluate the architecture instead of asking them to trust a benchmark.
